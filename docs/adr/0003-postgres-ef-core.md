# ADR-0003: Запросы PostgreSQL через EF Core (LINQ)

**Status:** Accepted
**Date:** 2026-11-03
**Deciders:** владелец бота

## Context

После ADR-0002 Postgres-репозитории строили SQL вручную (строки с `$1`, чтение колонок по порядку).
Владелец попросил перевести запросы на EF Core LINQ, а то, что через LINQ невозможно, оставить SQL.
ADR-0001 отверг EF Core как общий механизм всех хранилищ (Unit of Work, нет файлового провайдера,
атомарность расползается). Здесь EF — только деталь реализации одного провайдера; интерфейсы,
Json и SQLite не меняются.

## Decision

1. `BotDbContext` сопоставляет сущности с существующей схемой: snake_case, `ShortGuid` → `uuid`,
   время пишется в UTC и читается в локальном поясе (конвертеры), `digest_state` и `rate_limit` —
   служебные строки `DigestRow`, `RateLimitRow`. Контекст короткоживущий, из `PooledDbContextFactory`,
   отслеживание по умолчанию выключено.
2. **Схему создаёт не EF.** Миграций EF нет: `EnsureCreated` по-прежнему выполняет DDL и обновление
   версии схемы (ADR-0002) на SQL под advisory lock.
3. **LINQ:** все выборки, `Add`/`Update` (через `SaveChanges`), мягкое удаление и восстановление,
   `Reschedule`, `Snooze` (CASE через тернарный оператор), `Complete`, пользователи, сводка, лимиты,
   снимок. Атомарность без `ON CONFLICT` даёт:
   - условный `ExecuteUpdate` (один `UPDATE ... WHERE`): «выполнить, если не выполнена»,
     «восстановить, если удалён», «отметить сводку, если дата другая»;
   - уникальный индекс: вставка, которую опередил второй процесс, отклоняется (`23505`) — это
     означает «уже есть» (или повтор как обновление в `Upsert`).
4. **Остались на SQL:** DDL и обновление схемы, `pg_advisory_xact_lock`, `LOCK TABLE` при импорте,
   `COPY` журнала, и `TakeDueReminders` — `UPDATE ... RETURNING` (забрать и пометить одним
   оператором; в LINQ это «выбрать, потом пометить», и между ними второй процесс заберёт то же
   напоминание). Строки `RETURNING` материализует EF (`FromSqlRaw`).

## Trade-off Analysis

- **Плюс:** запросы типизированы — переименование свойства ловит компилятор, нет ручного порядка
  колонок; общие операции базового репозитория стали обобщёнными LINQ-запросами.
- **Минус:** `Upsert`, `AllowedUsers.Add`, `TryMarkDigest`, `SetRateLimit` — два запроса вместо
  одного `INSERT ... ON CONFLICT`; корректность при гонке держится на уникальных ключах.
  `Update` читает запись перед записью (последняя запись выигрывает, как и раньше).
- **Минус:** EF строит модель при старте процесса — MCP-сервер запускается на каждый запрос
  `claude`, это добавляет к старту время построения модели (порядка сотни миллисекунд).
  Если станет заметно — скомпилированная модель (`dotnet ef dbcontext optimize`).

## Consequences

- Новая сущность в Postgres: свойство в модели (`EntityTable<T>` в `BotDbContext`) и таблица в схеме;
  колонки сопоставляются по имени автоматически.
- Поведение проверяется теми же контрактными тестами, включая конкурентный `TakeDueReminders`.
