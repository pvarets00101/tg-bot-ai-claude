# ADR-0001: Подменяемое хранилище данных (ClaudeTelegramBot.Domain / .Storage)

**Status:** Accepted; решение 1, «Тип id» и «Миграции схемы» уточнены в [ADR-0002](0002-bazovaya-sushchnost-i-repozitoriy.md)
**Date:** 2026-11-03
**Deciders:** владелец бота

## Context

Бот и MCP-сервер (отдельный процесс, его запускает `claude -p` на каждый запрос) работают с общими
данными: заметки и задачи, сессии, модель чата, статистика и лимиты, список пользователей с доступом.
Сначала это были JSON-файлы, потом PostgreSQL. Нужно уметь выбирать хранилище конфигом
и в любой момент переносить данные между ними.

Ограничения:
- два процесса пишут одновременно, часть операций обязана быть атомарной
  (напоминание отправляется ровно один раз, сводка — раз в день);
- MCP-сервером управляет агент из Telegram, поэтому у него не должно быть лишних прав;
- нагрузка личная: единицы запросов в минуту, `Claude:MaxConcurrency = 1`.

## Decision

Два проекта, общие у бота и MCP-сервера: `ClaudeTelegramBot.Domain` (модели и интерфейсы
репозиториев, без зависимостей) и `ClaudeTelegramBot.Storage` (адаптеры). Сервисы бота и инструменты
MCP зависят только от `Domain`.

1. **Репозиторий на сущность с методами-намерениями** (`TakeDueReminders`, `Snooze`, `TryMarkDigest`,
   `Complete`), а не общий CRUD. Атомарность — забота адаптера: `UPDATE ... RETURNING` в SQL,
   межпроцессный мьютекс для файлов. `IStorage` собирает репозитории и умеет `Export`/`Import`
   полного снимка.
2. **Три адаптера на одном шве**: Json, Sqlite, Postgres. Выбор — `Storage:Provider`, строки
   подключения — `ConnectionStrings`. По правилу «один адаптер — гипотетический шов, два — настоящий»
   шов оправдан: адаптеры реально используются и проверяются одними контрактными тестами.
3. **Перенос** — `migrate-storage <откуда> <куда>`: снимок, импорт только в пустое хранилище,
   сверка после импорта. Источник не меняется.
4. **Синхронный интерфейс репозиториев** (см. компромиссы).
5. **Список пользователей** — в хранилище, при старте загружается в `AllowedUsers` (FrozenSet);
   изменения подхватываются перезапуском.
6. **PostgreSQL под ролью приложения `claude_bot_app`** без прав суперпользователя
   (`deploy/postgres-app-role.sql`): владеет только своими таблицами, подключается только к своей базе.

## Options Considered

### Вариант A: Generic Repository / Unit of Work (EF Core)
*Позже EF Core взят для одного провайдера — PostgreSQL, без Unit of Work и миграций: [ADR-0003](0003-postgres-ef-core.md).*

| Dimension | Assessment |
|-----------|------------|
| Complexity | Med |
| Провайдеры | только реляционные; файлы не встраиваются |
| Атомарность | приходится собирать из Get+Update, теряется на файлах |

**Pros:** привычно, миграции EF. **Cons:** нет файлового хранилища, атомарные операции
расползаются по вызывающему коду (нет locality), медленнее старт MCP-сервера на каждый запрос.

### Вариант B: Репозитории-намерения + фабрика провайдеров (выбран)
| Dimension | Assessment |
|-----------|------------|
| Complexity | Med: три реализации |
| Провайдеры | любые, включая файлы |
| Атомарность | внутри адаптера, проверена тестами |

**Pros:** глубокие модули — маленький интерфейс, сложность (блокировки, транзакции) спрятана;
одинаковое поведение гарантируют контрактные тесты. **Cons:** новый метод — правка трёх адаптеров.

### Вариант C: Только PostgreSQL
**Pros:** одна реализация. **Cons:** не выполняет требование «разные хранилища»; без сервера бот не работает.

## Trade-off Analysis

**Синхронный интерфейс.** Скилл `csharp-async` советует не смешивать блокирующий и асинхронный код,
а обработчики бота асинхронные. Оставлено синхронно, потому что:
- Json-адаптер держит именованный `Mutex`, а он привязан к потоку: его нельзя удерживать через
  `await`, асинхронная версия потребовала бы другого механизма межпроцессной блокировки;
- вызовы занимают миллисекунды на локальной базе, параллелизм бота — 1, пул потоков не страдает.

Пересмотреть, если база станет удалённой (сетевые задержки) или вырастет параллелизм: тогда
`I...Repository` → `...Async` с `CancellationToken`, Json — на файловую блокировку (`FileShare.None`).

**Роль-владелец, а не только DML.** Схему создаёт само приложение (`EnsureCreated`), поэтому роль
владеет таблицами. Разделение на «мигратор» и «DML-роль» строже, но требует второго набора
учётных данных; для личного бота главное — убрать суперпользователя (`COPY ... TO PROGRAM`,
доступ к другим базам).

## Consequences

- Легче: сменить хранилище (одна настройка + `migrate-storage`), тестировать (контрактные тесты),
  добавить провайдер (реализовать `IStorage`, ветка в `StorageFactory`, подключить к тестам).
- Сложнее: каждое изменение данных — в трёх адаптерах.
- Пересмотреть:
  - **Миграции схемы.** Сейчас схема — идемпотентный `CREATE ... IF NOT EXISTS`: новые таблицы и
    индексы добавляются сами, но изменение существующих колонок не применится к уже созданным базам.
    При первой такой правке — таблица версии схемы и упорядоченные шаги для каждого провайдера.
  - **Тип id.** `integer` (≈2 млрд) вместо рекомендуемого `bigint` — id видны пользователю как «#12»
    и модель на `int`; для личных заметок запаса хватает.
  - Синхронный интерфейс — см. выше.
